## 第一模块：核心理念与职责定位（1 小时）

### 1.1 GPS 家谱证据标准

**什么是 GPS？** Genealogical Proof Standard（家谱证据标准）

| 要素 | 说明 | 系统落实 |
|------|------|---------|
| **合理调研** | 全面收集所有可用来源 | sourceTags 数组字段 |
| **完整准确引用** | 每条信息标注出处 | metadata 规范化存储 |
| **冲突分析** | 识别并解决矛盾证据 | confidence 置信度标记 |
| **严密逻辑** | 推导过程可验证 | relation 关系图谱校验 |
| **结论撰写** | 最终结论清晰明确 | audit_logs 双人审核记录 |

## 第二模块：核心操作流程（3 小时）

### 2.1 入谱审核全流程演示

#### Step 1: 查看待审核工单列表

**操作路径**: `Admin Dashboard → Entry Records → Pending`

```sql
-- 查询条件
SELECT * FROM entry_records 
WHERE status = 'SUBMITTED' 
ORDER BY created_at DESC;
```

**审核要点**:
- ✅ 必填字段完整性（姓名/性别/出生日期）
- ✅ 证据上传完整性（至少 1 个来源标注）
- ✅ 世代连续性校验（父代=g → 子代=g+1）
- ✅ 谱名冲突检测（同世代谱名唯一性）

#### Step 2: 初审（BRANCH_HEAD/HOUSE_HEAD）

**审核动作选项**:
- ✅ `FIRST_PASS` - 初审通过，进入复审
- ❌ `REJECT` - 驳回（必填填写理由）

**初审检查清单**:
```markdown
- [ ] 申请人身份验证完成
- [ ] 父亲/母亲信息准确无误
- [ ] 出生公历/农历双记格式正确
- [ ] 照片/文档清晰可读
- [ ] 无重复人员存在（四维匹配检测）
```

#### Step 3: 复审（HISTORIAN+��

**审核动作选项**:
- ✅ `SECOND_PASS` - 复审通过，进入公示期
- ❌ `REJECT` - 驳回（族史委专属权限）

**复审特殊要求**:
1. **学术严谨性审查**:
   - 来源标注是否满足 GPS 标准
   - 关键信息（生卒/婚姻/迁徙）是否有证据支持
   - 置信度等级是否合理（⭐⭐⭐⭐⭐ vs ⭐）

2. **合法性审查**:
   - 是否违反分支编码规范
   - 是否存在跨支重复（需手动确认）
   - 是否触发公示期（默认 7 天）

#### Step 4: 公示期管理

**自动触发机制**:
```javascript
// config.json 配置项
{
  "publicityDays": 7,
  "allowedRolesToView": ["MEMBER", "BRANCH_HEAD", "HOUSE_HEAD", "HISTORIAN"],
  "notificationChannels": ["微信模板消息", "SMS"]
}
```

**公示期间异常处理**:
- 收到举报 → 暂停生效 → 启动调查流程
- 无人举报 → 公示期满 → 自动转为 APPROVED

#### Step 5: 最终入库

**自动化挂接**:
```javascript
const finalizePatch = async (recordId) => {
  // 1. 插入 member 集合
  await members.insert(record.payload);
  
  // 2. 创建 parent-child 关系边
  await relations.insert({
    fromId: childId,
    toId: parentId,
    type: 'PARENT_CHILD',
    status: 'ACTIVE'
  });
  
  // 3. 更新 path 字段（物化路径）
  const newPath = `${parent.path}${child._id}/`;
  await members.update({ _id: childId }, { $set: { path: newPath } });
  
  // 4. 生成 audit_log 记录
  await audit_logs.insert({
    action: 'entry.finalize',
    recordId,
    finalizedBy: currentUserId
  });
};
```

### 2.2 GEDCOM 导入导出实战

#### 场景 A: 从外部平台迁移数据

**步骤 1: 准备 GEDCOM 文件**
- 格式要求：GEDCOM 5.5.1 或 7.0
- 编码：UTF-8（无 BOM）
- 大小限制：≤100MB

**步骤 2: 执行导入**

```bash
# API 调用示例（实际在云函数中执行）
POST /cloud/functions/gedcom/index.js
{
  "action": "import",
  "fileUrl": "cloud-storage/path/to/file.ged"
}
```

**步骤 3: 预览校对**

**关键检查点**:
- ✅ 人数统计一致（source 计数 vs target 计数）
- ✅ 关系连通性（BFS 遍历全图）
- ✅ 日期格式标准化（ISO8601）
- ✅ 地名规范化（行政区划编码映射）

**步骤 4: 分批提交审核**

**批量策略**:
- 按世代分组（每代一个批次）
- 优先导入在世老人（高优先级）
- 老谱数字化内容单独审核

#### 场景 B: 对外共享数据

**导出格式选择**:

| 格式 | 用途 | 接收方 |
|------|------|--------|
| **GEDCOM 5.5.1** | 跨平台迁移 | Family Tree DNA / Ancestry |
| **GEDCOM-X XML** | FamilySearch 集成 | FamilySearch API |
| **RDF/Turtle** | 语义网/Linked Open Data | 学术研究机构 |
| **JSON** | AI 训练数据 | 内部算法模型 |
| **PDF 谱书** | 印刷版本 | 村民大会展示 |

**导出 SOP**:
```markdown
1. 选择导出范围（全族/分支/特定世代）
2. 勾选元数据字段（sourceTags/confidence）
3. 设置隐私保护（敏感信息脱敏）
4. 点击 Export → 下载本地
5. 云端冷备归档（保留 90 天）
```

### 2.3 迁徙管理与分支合并

#### 分支合并操作指南

**触发条件**:
- 两个分支确认为同一支系（历史考证）
- 始迁祖相同且世代连续
- 源分支已完全迁出或合并

**操作流程**:

1. **准备阶段**:
   ```sql
   -- 识别重复人物（四维匹配）
   SELECT a.*, b.* 
   FROM members a, members b
   WHERE a.branchCode = 'HAO-旧支'
     AND b.branchCode = 'HAO-新支'
     AND a.name = b.name
     AND a.generation = b.generation
     AND a.fatherId = b.fatherId
   ORDER BY a.generation;
   ```

2. **冲突标识**:
   - 人工标注疑似重复节点
   - 生成冲突报告 PDF

3. **合并执行**:
   ```javascript
   const mergeBranches = async (sourceBranch, targetBranch) => {
     // 1. 更新成员 branchCode
     await members.updateMany(
       { branchCode: sourceBranch.code },
       { $set: { branchCode: targetBranch.code } }
     );
     
     // 2. 删除源分支记录
     await branches.deleteOne({ code: sourceBranch.code });
     
     // 3. 更新人口统计数据
     await branches.increment(targetBranch.code, 'population');
     
     // 4. 记录合并审计日志
     await audit_logs.insert({
       action: 'branch.merge',
       source: sourceBranch.code,
       target: targetBranch.code,
       mergedAt: new Date()
     });
   };
   ```

4. **公告发布**:
   - 族内微信群通知
   - 首页轮播公告
   - 相关页面底部提示

## 第三模块：数据质量管控（1 小时）

### 3.1 数据质量检查清单

#### 维度一：完整性（Completeness）

| 检查项 | 验收标准 | 工具支持 |
|--------|---------|---------|
| 必填字段 | 100% 非空 | schema.required validation |
| 来源标注 | ≥1 个 sourceTag | schema.array validation |
| 证据附件 | 关键信息有文档/图片 | manual review checklist |
| 双语日期 | 公历 + 农历双记 | birthDate/deathDate 格式检查 |

#### 维度二：准确性（Accuracy）

| 检查项 | 验收标准 | 工具支持 |
|--------|---------|---------|
| 世代连续 | 父子世代差=1 | relation-spouse.test.js 校验 |
| 日期合理性 | 生 < 死 < 现在 | date-validator 库 |
| 谱名唯一 | 同世代同分支不重复 | unique index 约束 |
| 称谓逻辑 | 辈分差符合常理 | kinship-title.js 反向校验 |

#### 维度三：一致性（Consistency）

| 检查项 | 验收标准 | 工具支持 |
|--------|---------|---------|
| 分支归属 | 每个成员属于唯一分支 | branchId required |
| 始祖链完整 | 所有祖先路径闭合 | lineage-naming.test.js |
| 字辈对齐 | generationChar 与 generations 表一致 | generation.matchGen() |
| 关系双向 | PARENT_CHILD↔CHILD_PARENT 成对 | graph-closure check |

## 第四模块：常见问题解答（1 小时）

### Q1: 如何判断某个证据的可靠性？

**A: 采用五档评级法**

| 星级 | 标准 | 示例 |
|------|------|------|
| ⭐⭐⭐⭐⭐ | 确凿无疑 | 官方档案原件、DNA 验证、碑刻拓片 |
| ⭐⭐⭐⭐ | 高度可信 | 两本以上独立家谱一致记载 |
| ⭐⭐⭐ | 基本可信 | 单一可靠来源（县志/方志） |
| ⭐⭐ | 有待考证 | 口述历史记录（无实物佐证） |
| ⭐ | 存疑 | 传说/民间故事 |

**实操建议**:
- 初始录入时选择保守评级（低星）
- 随着证据积累逐步升级
- 最终结论应以最高星标证据为准

### Q2: 发现已入库成员的世代计算错误怎么办？

**A: 修复流程**

1. **锁定影响范围**:
   ```javascript
   const affectedMembers = fetchDescendants(wrongMemberId);
   // 获取所有后代，重新计算世代数
   ```

2. **批量更新**:
   ```javascript
   await Promise.all(affectedMembers.map(m => 
     members.update({ _id: m._id }, { 
       $set: { 
         generation: correctedGeneration,
         version: m.version + 1,
         updatedBy: currentUserId
       }
     })
   ));
   ```

3. **生成修正报告**:
   - 列出修正的人员名单
   - 说明修正原因（原世代数→现世代数）
   - 附上校正依据（文献/推理过程）

4. **审计追踪**:
   - 记录修正操作的 user_id 和时间戳
   - 保留旧值快照（v-1 版本）
   - 生成 changelog.md

### Q3: 遇到跨支人员重复，但无法确定归谁？

**A: 暂存待查机制**

1. **标记为"待确认"状态**:
   ```json
   {
     "_id": "pending-001",
     "name": "郝某",
     "generation": 15,
     "status": "PENDING_CLARIFICATION",
     "duplicateCandidates": [
       { "branchId": "HAO-赵县 -001", "confidence": 0.6 },
       { "branchId": "HAO-宁晋 -002", "confidence": 0.4 }
     ]
   }
   ```

2. **启动调查流程**:
   - 联系两地支长核实
   - 查阅两地家谱原始版本
   - 必要时实地走访

3. **决策结果处理**:
   - 若确定归属 → 正式入库至对应分支
   - 若仍无法确认 → 暂时放入总谱 HAO-0000 待查区
